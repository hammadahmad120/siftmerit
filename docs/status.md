- **Built so far:** the repo root (npm workspaces, shared TypeScript settings, `.env.example`) and four parts. The API in `services/api` checks who is calling and which company they belong to, and has these addresses: `/v1/health`; `/v1/me`, which answers with the signed-in user's company and role; `/v1/jobs` (`POST` saves a new job, `GET` lists the company's newest 100) and `/v1/jobs/:jobId` (one job, or 404); and `/v1/demo-work` (`POST` starts a demo run, `GET` lists the company's last ten runs). It reaches Supabase with the secret key, gives every log line a request ID, answers errors in one clean shape, reads a body of at most 100 KB and allows the web app's address through CORS. It also holds the scripts behind `npm run company:create`, `npm run company:add-user` and `npm run ai:check`. Core in `packages/core` holds the winston logger, the settings loader, the database connection, the helper `forTenant` that always adds the company filter, the repositories for `jobs`, `work_runs` and `ai_calls` (all reach their table only through the helper), the AI wrapper and the work queue (BullMQ on Redis, one queue named `demo`), and is read as TypeScript source in development. The worker in `services/worker` keeps running: it listens to the queue, runs each demo work item, keeps the run's row in Postgres in step (waiting, running, done or failed), tries a failed item again up to three times, and finishes the running item before it stops. It also holds three development scripts, `npm run mailbox:connect`, `npm run mailbox:check` and `npm run test-set:send`. The web app in `apps/web` (Next.js 16) has sign-in and sign-out and a shell around every signed-in page: a top bar with the product's name, a menu of two items (Home, Jobs), the company name, the user's email and a "Sign out" button. Its pages are a sign-in page at `/signin`; a home page at `/` with a "Jobs" section and a temporary "Queue demo" section; the job list at `/jobs`, drawn as cards with a "New job" button; the form at `/jobs/new` with a title, a job description, subject words entered as chips and a posting date; and a job's own page at `/jobs/<id>`. The last two have a "Back to jobs" button. The shell asks `/v1/me` once and shares the answer with every page through a React context (`useMe()`). The look is set: light mode only, the navy, cream, purple and light navy of the NexRhino colour guide written once in `globals.css`, navy buttons, links that look like buttons and form fields from shared constants, and the Geist font. The session is kept in the browser's local storage by the Supabase library, a browser-side guard sends a visitor with no session to the sign-in page, and every screen calls the API through the helper `apiFetch`, which attaches the token itself. The web app has ESLint with the Next.js rules. How it all works is in `docs/developer-guide.md` (jobs are section 10), and the table map is in `docs/table-map.md`.
