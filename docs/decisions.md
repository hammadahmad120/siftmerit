## Product and code

| Date | Decision | Why |
|---|---|---|
| 2026-11-16 | The work queue is BullMQ on Redis, not a `work_queue` table in Postgres polled by the worker. RabbitMQ is not used. InstantBot's queue code (`channel-message-queue.ts`, `worker-loop.ts`) is no longer copied. This changes `tech-plan.md` sections 3 to 7 and the task list. | The user wants to learn Redis and BullMQ, which most Node teams use. Postgres polling was simpler for a pilot and was the earlier recommendation. RabbitMQ is made for passing messages between many services and has no natural place here. |
| 2026-11-16 | What HR sees (status, progress, skip reasons) is saved in Postgres, never read from Redis. A work item is added to the queue after its Postgres row is saved, the row is marked failed if adding throws, and every handler is safe to run twice. | With a queue outside the database, the row and the queued item can disagree if one write fails. |
| 2026-11-16 | Background work is still called a "work item" in our code and screens, although BullMQ calls it a "job". | "Job" already means a hiring job. |
| 2026-11-16 | Redis is installed on the development machine from Redis's official package source, by the user, in the first queue task. | Ubuntu 22.04's own package gives Redis 6.0.16, which is older than the version BullMQ is remembered to recommend. The exact minimum is checked in the BullMQ docs in that task. |
| 2026-11-17 | Task 1: the table map has 12 tables: `tenants`, `tenant_members`, `mailbox_connections`, `jobs`, `job_requirements`, `job_emails`, `candidates`, `applications`, `ticks`, `work_runs`, `chat_messages`, `ai_calls`. The map is in `docs/table-map.md`. | Agreed with the user after going through each table. |
| 2026-11-17 | A candidate is stored once per company. An application is that candidate in one job. Ticks belong to one application and one requirement. | A saved candidate can be brought into a new job by adding one application row. Copying the person into each job would store the CV twice and make delete-on-request easy to get wrong. |
| 2026-11-17 | Requirements are their own table, not a list inside the job row. Ticks are their own table, not a list inside the application row. | Each tick must point to one requirement, so removing, adding or rewording one requirement touches one row per candidate and never rewrites the rest. |
| 2026-11-17 | `job_emails` keeps one light row per email per job: Gmail's email ID, subject, sender, date, picked or not, status and skip reason. No body and no attachment. A bookmark alone is not used. | HR picks groups, CVs are read side by side and some fail, so "everything before this point is done" is not true. The worker asks for waiting emails, oldest first, so early applicants go first. |
| 2026-11-17 | The job row keeps a "last checked" time, used only to ask Gmail for new mail. The exact method is settled in task 45. | The daily check should not list the whole mailbox again. The email list drops any ID it already has. |
| 2026-11-17 | Because the email list is per job, an email that matches two open jobs is read once for each job and makes two candidate rows. Accepted for the pilot. | A per-company email list needs one more table and more complex mailbox code, for a case that should be rare. |
| 2026-11-17 | Status rows for queued work live in one small table, `work_runs`: kind of work, status, error, start and end time, with an optional link to a job. The progress number is counted from the `job_emails` rows. | One job has many pieces of work over time, so one status column on the job is not enough, and tasks 9 and 10 need a status row before jobs exist. | 2026-11-17 | The mailbox secret is kept in its own table, `mailbox_connections`, not as a column on `tenants`. | InstantBot's row rules let a signed-in user read their own `tenants` row. |
| 2026-11-17 | Product change to step 3: saved candidates are not checked automatically for every new job. When creating a job, HR picks which past jobs to bring saved candidates from, and confirms before AI is used. The same job with more openings stays as "reopen" (task 50). `product-flow.md` step 3 and the task 49 row in `tech-plan.md` are updated in the task 1 wrap-up. | Checking every saved candidate costs one AI call each and is wasted when the new job is a different kind of job. | 2026-11-17 | Task 2: the package manager is npm, with npm workspaces. | It is already installed and is what InstantBot uses, so copied files and commands fit without changes. |
| 2026-11-17 | Task 2: the API runs on port 4100. | InstantBot's API uses 4000, so both projects can run at the same time. |

The request ID is given by our own small middleware, not another library. | The user's choice after comparing it with pino.
