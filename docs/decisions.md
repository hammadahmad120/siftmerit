# Decisions

One line per decision, written at the moment it is settled. Newest at the bottom of each table. Decisions made before 2026-11-13 are in [tech-plan.md](tech-plan.md) section 3. Task numbers follow the 53-task list of 2026-11-16 in [tech-plan.md](tech-plan.md) section 8.

## How we work

| Date | Decision | Why |
|---|---|---|
| 2026-11-13 | `CLAUDE.md` holds the product summary, the workflow, the rules and the structure. It is loaded in every session and stays short. | It is read every session, and a long file means the rules get less attention. |
| 2026-11-13 | `docs/status.md` is pulled into `CLAUDE.md` automatically. The product flow and the technical plan are read only when a task needs them. | Loading both long documents every session costs tokens and hides the short rules. |
| 2026-11-13 | Every task follows the eight-step workflow in `CLAUDE.md`, with two go-aheads: one for the plan and one to start building. | The user wants discussion and a reviewed plan before any code is touched. |
| 2026-11-13 | No decision is made on an assumption. The list of what must be confirmed first is in `CLAUDE.md` under "Decisions". Small details that follow from the plan or an existing pattern need no question but are listed in the Explain step. | The user wants to confirm every real decision, without being stopped for variable names. |
| 2026-11-13 | After every task, small or big, the work is explained in simple words, with the steps to validate it. | The user wants to understand how each task was built and how it works. |
| 2026-11-13 | A developer guide, `docs/developer-guide.md`, is kept up to date in every wrap-up. It is organised by part of the product and describes what exists now. It is created at the end of task 4, when the API, worker and web app all exist. | A new developer needs one place to learn the product. Before that there is nothing real to write in it. |
| 2026-11-13 | Docs are synced only after the user confirms the task works. Decisions are the exception: they are written when settled. | Docs should never describe something broken, and a decision recorded late can be missed. |
| 2026-11-13 | At the start of every session the status is compared with the git state. | It catches a wrap-up that was missed. |
| 2026-11-13 | No separate change log. Code changes are recorded in git commit messages. | A second copy would fall out of date. |
| 2026-11-13 | No rules files, skills, subagents or hooks for now. A hook for the type check is added if it is ever skipped. A permission list in `.claude/settings.json` is considered after task 4. | The docs cover the need, and each extra is one more thing to maintain. |
| 2026-11-13 | Commits are made only when the user asks. The InstantBot and mailsift repos are treated as read-only unless the user says otherwise. | Both keep changes under the user's control. |
| 2026-11-13 | If `tech-plan.md` sections 2 or 7 differ from `CLAUDE.md`, `CLAUDE.md` wins. `tech-plan.md` is the plan agreed on 2026-11-12 and revised on 2026-11-16. | Each rule should have one place where it is current. |
| 2026-11-16 | Task size rule: one new idea per task, one result that can be seen, and a diff that can be read in one sitting. Code copied from InstantBot counts toward the size and is explained as if the user has never seen InstantBot. | The user wants to understand 100% of what each task builds before moving to the next one. |

Each table's SQL is written in the task that first needs it, not all up front. | A table is easier to review beside the code that uses it, and the map stops an early task from saving data in a shape a later task must rewrite. |
| 2026-11-16 | A small mailbox check is added early, as task 5: run mailsift over HTTP and list a few emails from the development mailbox. | The Google setup and token expiry are the biggest unknowns and would otherwise first appear at the mailbox tasks (20 onward). |
| 2026-11-16 | Tests and evals are written for the major items only, not for the whole codebase. Which items, and in which tasks, is settled when the task list is drafted. This replaces "no tests until the pilot readiness task". | People ask how the product was validated before production, and the scoring and AI parts are where a silent mistake hurts most. |
| 2026-11-16 | Rules for a task: (1) one result that can be checked, with a one-sentence "how to check it"; (2) one main new idea; (3) ceiling of one sitting, starting at about 400 lines to read and about 10 files, adjusted after the first tasks; (4) no setup-only tasks, setup joins the first thing that uses it; (5) thin slices through database, API and screen, not layers, except pure-code pieces that show a result alone; (6) the product runs and the type check passes after every task; (7) a task that is too big is split in the plan step, not during the build. | Tasks must be small enough to discuss and review fully, but big enough to deliver something that can be validated. |
| 2026-11-16 | Three kinds of task: build (code that runs), design (a doc the user approves) and decision (a choice that affects several tasks or needs a test to answer). Other choices are settled in the discuss step of the build task that needs them. | Giving every small choice its own task would double the list and add no value. |
| 2026-11-16 | Scope of tests: scorer, masking, proof-line check, company separation. Scope of evals: requirements draft, the CV check and fact sheet, ticks with proof lines, hidden instructions in a CV, and the top five against HR's pick. Tests go inside the task that builds the piece. The eval runner is its own task, and each later eval is a small task after its feature. Everything else is checked by hand. | These are the parts with one right answer or where AI quality must be measured. Screens and routes do not need it for a pilot. |

| 2026-11-16 | No test CVs exist yet. They must be gathered before the mailbox tasks, and the same set serves the test mailbox, the evals and the model comparison. | Checked with the user. |
| 2026-11-16 | The test CV set is a mix: about 30 AI-written CVs, each made from a fact card written first; about 10 real CVs collected by the user with permission; about 10 junk and hard cases (invoice PDF, newsletter, scanned CV, `.doc` file, duplicate, a CV with a hidden instruction). ## Product and code

| Date | Decision | Why |
|---|---|---|
| 2026-11-16 | The work queue is BullMQ on Redis, not a `work_queue` table in Postgres polled by the worker. RabbitMQ is not used. InstantBot's queue code (`channel-message-queue.ts`, `worker-loop.ts`) is no longer copied. This changes `tech-plan.md` sections 3 to 7 and the task list. | The user wants to learn Redis and BullMQ, which most Node teams use. Postgres polling was simpler for a pilot and was the earlier recommendation. RabbitMQ is made for passing messages between many services and has no natural place here. |
| 2026-11-16 | What HR sees (status, progress, skip reasons) is saved in Postgres, never read from Redis. A work item is added to the queue after its Postgres row is saved, the row is marked failed if adding throws, and every handler is safe to run twice. | With a queue outside the database, the row and the queued item can disagree if one write fails. |
| 2026-11-16 | Background work is still called a "work item" in our code and screens, although BullMQ calls it a "job". | "Job" already means a hiring job. |
| 2026-11-16 | Redis is installed on the development machine from Redis's official package source, by the user, in the first queue task. | Ubuntu 22.04's own package gives Redis 6.0.16, which is older than the version BullMQ is remembered to recommend. The exact minimum is checked in the BullMQ docs in that task. |
| 2026-11-17 | Task 1: the table map has 12 tables: `tenants`, `tenant_members`, `mailbox_connections`, `jobs`, `job_requirements`, `job_emails`, `candidates`, `applications`, `ticks`, `work_runs`, `chat_messages`, `ai_calls`. The map is in `docs/table-map.md`. | Agreed with the user after going through each table. |
| 2026-11-17 | A candidate is stored once per company. An application is that candidate in one job. Ticks belong to one application and one requirement. | A saved candidate can be brought into a new job by adding one application row. Copying the person into each job would store the CV twice and make delete-on-request easy to get wrong. |
| 2026-11-17 | Requirements are their own table, not a list inside the job row. Ticks are their own table, not a list inside the application row. | Each tick must point to one requirement, so removing, adding or rewording one requirement touches one row per candidate and never rewrites the rest. |
| 2026-11-17 | `job_emails` keeps one light row per email per job: Gmail's email ID, subject, sender, date, picked or not, status and skip reason. No body and no attachment. A bookmark alone is not used. | HR picks groups, CVs are read side by side and some fail, so "everything before this point is done" is not true. The worker asks for waiting emails, oldest first, so early applicants go first. |
| 2026-11-17 | The job row keeps a "last checked" time, used only to ask Gmail for new mail. The exact method is settled in task 45. | The daily check should not list the whole mailbox again. The email list drops any ID it already has. |
| 2026-11-17 | Because the email list is per job, an email that matches two open jobs is read once for each job and makes two candidate rows. Accepted for the pilot. | A per-company email list needs one more table and more complex mailbox code, for a case that should be rare. |
| 2026-11-17 | Status rows for queued work live in one small table, `work_runs`: kind of work, status, error, start and end time, with an optional link to a job. The progress number is counted from the `job_emails` rows. | One job has many pieces of work over time, so one status column on the job is not enough, and tasks 9 and 10 need a status row before jobs exist. A row per queued item would be a second queue in Postgres. |
| 2026-11-17 | The mailbox secret is kept in its own table, `mailbox_connections`, not as a column on `tenants`. | InstantBot's row rules let a signed-in user read their own `tenants` row. |
| 2026-11-17 | Product change to step 3: saved candidates are not checked automatically for every new job. When creating a job, HR picks which past jobs to bring saved candidates from, and confirms before AI is used. The same job with more openings stays as "reopen" (task 50). `product-flow.md` step 3 and the task 49 row in `tech-plan.md` are updated in the task 1 wrap-up. | Checking every saved candidate costs one AI call each and is wasted when the new job is a different kind of job. HR knows which past jobs are relevant. It also fits the rule that actions costing AI money need a confirm click. |
| 2026-11-17 | "Start from a past job" (prefill the description and requirements of a new job from an old one) is left out of the pilot. | HR can paste the text. It can be added later without changing the tables. |
| 2026-11-17 | Task 2: the package manager is npm, with npm workspaces. | It is already installed and is what InstantBot uses, so copied files and commands fit without changes. |
| 2026-11-17 | Task 2: the API runs on port 4100. | InstantBot's API uses 4000, so both projects can run at the same time. |
| 2026-11-17 | Task 2: the logger is winston, at its newest version. It prints structured lines in production and easy-to-read lines on the development machine, both from winston's own formats, so no second tool is needed. The request ID is given by our own small middleware, not another library. | The user's choice after comparing it with pino. Both do the job. pino was the first recommendation because it prints structured lines with no setup; winston needs a few lines of setup but has readable development output built in. Every log line must carry a request ID or a work item ID, and InstantBot has no logger to copy. The same "logger with an ID attached" idea is reused in the worker. |
| 2026-11-17 | Task 2: the logger file lives in the API for now and moves to `packages/core` in task 3. | The worker needs it too, but the shared package does not exist until task 3. Creating it now would pull task 3's main idea into task 2. |
| 2026-11-17 | Express and TypeScript stay on the major versions InstantBot uses (Express 4, TypeScript 5), not the newest (5 and 7 on 2026-11-17). | Code copied in later tasks was written and tested on those versions. Upgrading later is a contained job on a small codebase. |
| 2026-11-17 | zod is version 4, not the version 3 that InstantBot uses. This replaces the first choice of zod 3, made earlier the same day. Code copied from InstantBot that uses zod is checked against zod 4 in the task that copies it. | `npm install` reported a high-severity warning for every zod below 4.6.6 (it can use up memory when checking a very large list), and no fixed version 3 exists. Later tasks use zod to check data sent to the API and answers from the AI, which is where that matters. Only two files used zod when the switch was made. |
| 2026-11-17 | Task 2 copies five of the seven API skeleton files listed in `tech-plan.md` section 6: `app.ts`, `index.ts`, `config/env.ts`, `lib/errors.ts` and `middleware/error.middleware.ts`, each cut down. `lib/supabase.ts` waits for task 6 and `lib/rate-limiter.ts` waits until something needs limiting. | Setup joins the first thing that uses it. |
| 2026-11-17 | The env file holds only the settings the code uses at that point. In task 2 that is the API port and the log level. Each later setting is added by the task that first uses it. | An unused setting cannot be checked and hides the ones that matter. |
| 2026-11-17 | One shared TypeScript settings file at the repo root (`tsconfig.base.json`) that each part extends. | InstantBot keeps three near-identical copies, which can drift apart. |
| 2026-11-17 | Task 2: the health check answers a plain "ok" with no database check. | There is no database yet. |
| 2026-11-17 | Logs are printed as structured lines to the terminal (standard output). In production the hosting service collects and keeps them. Nothing HR needs is kept only in logs. | The API does not need to know where logs end up, so the same code works locally and when deployed. Where they are kept is decided with the deployment target in task 53. |
| 2026-11-17 | Rule for all code: log lines hold IDs only, such as the request ID, work item ID, job ID and email ID. They never hold CV text, email content, names, contact details or secret keys. The rule is added to `CLAUDE.md` in the task 2 wrap-up. | Production logs are kept by an outside service and CVs hold personal data. A debugging line with personal data in it is an easy privacy leak and is harder to clean up later than to forbid from the start. |
| 2026-11-17 | The app does not write log files itself. | On most hosting services the disk is wiped on each deploy, files grow until the disk is full, and several running copies would each have their own file. If a file is ever wanted, winston can write one by adding a file output in the logger setup. |

## Open points for later tasks

Raised in discussion and **not decided**. Each is settled inside its task.

| 24 | Where HR's remembered subject picks are kept | A small table or a column on the job. Not discussed yet. |

| 35, 36 | Whether the score is saved or worked out when shown | Not discussed yet. A saved score can go out of date when strict or lenient is changed. |
| 45 | How the "last checked" time is used | Ask Gmail with a small overlap and let the email list drop IDs it already has. |

| 49 | Bringing saved candidates into a new job | Open: whether a job that is still open can be picked, and whether ticks can be reused for requirements that did not change. |
| 28, 33 | Masking and the proof-line check | The AI sees masked CV text, so the proof-line check must compare against the masked text, not the original. |
| 28 | Hiding names | Code can find emails and phone numbers by pattern, but not names. |
| 35 | Scoring gaps | "Mentioned only" has no point value yet. It is not stated whether an "unclear" must counts as the one missed must in lenient mode. |
| 20, 26 | Using Redis directly | Besides BullMQ, Redis could hold the mailbox token cache and the per-mailbox speed limit, so plain Redis is learned too. Raised, not confirmed. |
| 9 | Seeing queued items | A small dashboard library for BullMQ could show items while validating. Raised, not confirmed. |
| 9 | Redis version | BullMQ is remembered to work on Redis 5 and up and to recommend 6.2 or newer. Check the BullMQ docs before installing. |
| 13, 17, 47 | AI SDK details | InstantBot uses AI SDK v6. Check the current docs for tool calling and the MCP client before building, not memory. |
